    Adding a simulator to the registry¶

    In registry_env and in every composed environment (mash-ups included), compose-api runs a process class only if its module belongs to an entry at level tested or higher, as set in compose_api/registry/manifest.yaml or as computed from the compliance cases of the composed version (registry/validation.py). A prebuilt image's classes are not looked up: an administrator vouches for the image by registering it as a version (api/routers/simulation.py). This page is for anyone who wants a wrapper repository (a viva-* workspace, or any process-bigraph package) to run here, and for the person who reviews that change. The checklist is the pull request template registry-entry.md; this page says what it asks for and why.

    GitHub fills a pull request from a template in a PULL_REQUEST_TEMPLATE/ directory only when the compare URL names it: https://github.com/biosimulations/compose-api/compare/main...<branch>?quick_pull=1&template=registry-entry.md (GitHub: query parameters). Opened any other way, paste the template's text into the description.

    Three paths¶

    1. Listed through viva-catalog. This never runs. registry/catalog.py reads viva-catalog's modules.json and writes registry/catalog.yaml: every wrapper at level listed, pinned to the commit its branch pointed at that day. The file is generated and never edited by hand. The service runs tested or higher, so admission refuses a listed entry's classes. Listing makes a repository discoverable and grants nothing.
    2. A manifest entry, by pull request, at the level the evidence supports. The entry names the package, how it installs, the modules it provides and the evidence for its level. Entries change only by pull request, and an entry in manifest.yaml takes precedence over the catalog.yaml entry with the same id. Administrators register environment versions through the API, never entries.
    3. After the merge, below: a release, then a signed-in run builds the environment.

    After the merge¶

    • The manifest is a versioned file in the package, read at call time, so an entry takes effect with the next compose-api release.
    • An entry with empty bundles is in no declared environment. When nothing covers the entries a document names, the first run by a signed-in caller makes a mash-up of exactly those entries, with what they requires: a pixi.toml generated from the entries, locked in an unprivileged Job, built on the privileged builder, read back, and checked by each member entry's compliance cases (docs/plan-environment-composition.md, D7.4, D7.5). Later runs with the same set reuse that version.
    • An anonymous caller whose run needs a mash-up that does not exist gets a 401 and causes no build. At most two are locked or built at once, and a set of packages that conflict is a 409 with pixi's explanation (environments/lifecycle.py). If the first lock or build of a set fails, later runs of that set get a 409 until an administrator makes a new version.
    • The cases decide the entry's level in that version: tested when they pass, failed when one does not, untested without cases. An entry whose cases are still running is refused there until they finish; one with no cases, or whose cases cannot run (a missing file is a logged warning), keeps the manifest's level for admission (composition plan, 5b, 5c; environments/compliance_runs.py). A module of the entry that does not import in the version's image refuses every class under it there (module-imports).
    • Moving the pin is another manifest pull request and release; a pin that moves never starts a build by itself (D7.7).
    • Every composed version installs the core that environments.yaml names under composition.core when the version is made: process-bigraph 1.11.1 and bigraph-schema 1.8.3 (1.9.1 and 1.8.1 before). A version keeps the pixi.toml and the lock it was made with, and its image installs that lock unchanged (environments/service.py, environments/pixi.py), so a new core reaches only versions made after the release that carries it. Existing versions, mash-ups included, keep theirs, and later runs of the same set still use them. process-bigraph 1.11.1 no longer requires scipy, sympy or matplotlib, as 1.9.1 did, so an entry that imports one must declare it.
    • vivarium-tyssue's mash-up keeps its version on 1.9.1, which runs as before. On the current core its sheet-relaxation case fails while the composite is built: bigraph-schema 1.8.3 cannot merge a table (a Frame) with no update, which bigraph-schema 1.8.4 fixes (bigraph-schema #209), and process-bigraph 1.11.1 requires bigraph-schema below 1.8.4. A version made on this core that includes vivarium-tyssue therefore records it failed and refuses its classes. That version stays so: once process-bigraph allows 1.8.4 and the core moves to it, an administrator makes a new version of that environment, since a run makes only a mash-up's first version (D7.7).
    • A package that publishes its own image is registered by an administrator as a version of a named environment (D8.3), which needs its own line in environments.yaml.

    Writing the entry¶

    Preferred: generate it with vivarium-workbench compose-entry, which produces the entry and checks it (see its --help), and paste both into the pull request. A hand-written entry is accepted: copy the closest one in manifest.yaml and say in the pull request that it is hand-written, and why. By shape: viva-basic-processes (git, nothing else), pbsim-common (git with requires and types), viva-pde-particle (git with conda: engines, extras, and its own image), pb-multiscale-actin (a PyPI release), smoldyn-vcell (a wheel by URL and sha256).

    A component often needs library entries beside it (kind: library: an engine, or a pin on a floating dependency; install or conda, no module_roots). They install code like any other entry and are reviewed the same way. Their level gates nothing: what runs is a component's classes (environments/lifecycle.py, composable).

    An entry that provides the same simulator as an existing one (often the same class names) says so with alternative_to: <standard entry id>. The standard entry is what the service's own runs use (SED-ML solvers, suites); the alternative keeps its own level and runs where admitted, and the catalog shows it as an alternative. viva-copasi and viva-tellurium are alternatives to pbsim-common until the two families are reconciled. The standard entry must be a component that is not itself an alternative (tests/registry/test_manifest.py).

    Check that it locks¶

    A signed-in first run of an entry makes a mash-up of exactly that entry and what it requires: pixi_toml() writes a pixi workspace, an unprivileged Job locks it with pixi exec --spec git -- pixi lock in the image environments.yaml names, and a lock that does not resolve is recorded as a failed version. Later runs of that entry set then get a 409 until an administrator makes a new version (environments/service.py, environments/lifecycle.py), so an entry that cannot lock must not reach a release at tested, and no check above locks one. To run the same step before asking, in a clone of compose-api whose manifest.yaml has the entry (an entry that is only in catalog.yaml has no install, so there is nothing to lock):

    ENTRY=viva-ketchup      # the entry's id
W=$(mktemp -d)
uv run python - "$ENTRY" > "$W/pixi.toml" <<'PY'
import datetime
import sys

from compose_api.environments.pixi import DEFAULT_PYTHON_VERSION, ComposedSpec, pixi_toml
from compose_api.registry.environments import load_environments
from compose_api.registry.manifest import load_manifest

composition = load_environments().composition
entry = next(e for e in load_manifest().entries if e.id == sys.argv[1])
now = datetime.datetime.now(datetime.UTC).replace(microsecond=0)
spec = ComposedSpec("lock-check", (entry,), tuple(sorted(composition.core.items())), composition.platform, DEFAULT_PYTHON_VERSION, now)
print(pixi_toml(spec), end="")
PY
IMAGE=$(uv run python -c 'from compose_api.registry.environments import load_environments; print(load_environments().composition.pixi_image)')
docker run --rm --platform linux/amd64 --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$W":/work -w /work "$IMAGE" pixi exec --spec git -- pixi lock
grep '^- pypi: git+' "$W/pixi.lock" | grep -v '?rev='     # git sources pinned to no commit; empty is what is wanted

    --platform linux/amd64 is the Job's platform (on Apple silicon the arm64 image fails whenever a source build is needed); HOME=/tmp keeps pixi's cache inside the container (on macOS a cache on the mounted folder fails with "failed to link ... Invalid argument"). What a lock does not show: the privileged build, the run, this entry together with others, or a later day (exclude-newer is now, and a git branch tip moves).

    What CI checks¶

    These run on every pull request, so a change that breaks one is red before a reviewer reads it:

    • An entry is pinned by version or commit, has module_roots if it is a component, and ids are unique (registry/manifest.py).
    • An install names exactly one of pypi with its exact version, git with a full 40-character commit (never a branch), or url (an https .whl) with its sha256. requires names entries that exist.
    • Every entry above listed has evidence, and every library says how it installs (tests/registry/test_manifest.py).
    • Each declared environment still composes: no two entries install one distribution, no conda package is asked for with two specs, requires are listed, bundles and entries agree (registry/environments.py, tests/registry/test_environments.py).
    • Compliance cases are checked only for the entries a test names, today pbsim-common, viva-basic-processes and viva-pde-particle (tests/environments/test_compliance.py). No test walks every entry's cases, so a new entry's case is checked only by a test its pull request adds or by the reviewer, with the command in the template.
    • Whether an entry's environment locks is checked by none of these (see "Check that it locks").

    Locally: uv run python -m pytest tests/registry tests/environments/test_compliance.py -q (the database-backed tests need Docker), and make check for the lint and type checks (CLAUDE.md).

    What only a reviewer can check, and why¶

    • Provenance. An entry is pinned to a release or a commit (composition plan, "What is a safe component"). The reviewer approves that commit, not the repository, so the template asks who controls the repository, that the hash is on its default branch or a tag, and, for a new pin, which files changed since the old one. A commit on the default branch or a tag is also the test plan-entry-updates.md proposes for moved commits.
    • One hash, one repository. Only install.commit is validated, and it is what pixi installs (environments/pixi.py). commit: and the source URL are what people read, and nothing ties them to install: not the hash, nor the repository.
    • Install-time code. The build runs package code as root on the privileged builder, and locking reads package metadata, which can run build code, in an unprivileged Job (simulation/build_k8s.py). The reviewer reads the build backend, its requirements and any setup.py, hook or build script. A pypi pin is built too when the release has no wheel for the environment's Python, and for a url pin the reviewer asks how the wheel was built (the smoldyn-vcell entry names the workflow that built it).
    • Import-time code. process-bigraph builds its core with bigraph-schema's allocate_core, which imports the modules of every installed distribution that requires bigraph-schema (bigraph-schema 1.8.3, package/discover.py: is_process_library, load_local_modules). bigraph-schema caches that walk's index under ~/.cache/bigraph-schema, but a run starts the image with --compat, whose home is empty each time, so every run walks again. Import-time code in anything a wheel ships, and in every dependency that requires bigraph-schema, can therefore run whether or not a document names it. That is why the template asks about packages outside module_roots.
    • Distribution name. The generated pixi.toml keys the dependency by the name install derives (the repository's name for git), and two entries with one name are a composition problem. [project].name at the commit should be that name.
    • Dependencies. A composed environment installs the package's declared dependencies, so a development tool among them lands in every run image, and a git or URL reference is not covered by the pin. The pin freezes the package, not what it depends on: those resolve when the version is locked, no newer than the lock's exclude-newer date (environments/pixi.py). The composition also fixes Python and the core's process-bigraph and bigraph-schema versions (environments.yaml), so a package whose bounds exclude them cannot be locked with the others. viva-pde-particle keeps vivarium-workbench behind a workbench extra for this reason (its pyproject.toml). A git package's own [tool.uv.sources] are followed as well: a source that sends a dependency to a branch pins nothing, and the lock takes that branch's tip, and the tip's own sources, the day it runs ("Check that it locks" lists them).
    • Config-driven imports. The address check is the only gate (registry/validation.py) and sees only address values. A class that imports or runs what its config names escapes it: EnsembleRunner imported a module:function from its config, and viva-pde-particle#67 replaced it (composition plan, 7c-4). The types items are imported by the runner before every run (environments/runner.py), so each should be in the entry's own package. Code the config or a submitted file supplies is the same hole: vivarium-tyssue's SBMLCellCycle evaluates expressions from its config, so its module is not a root.
    • Submitted files a class deserializes. A file in the upload that a class unpickles runs code too. pandas unpickles HDF5 object columns and some attributes, and submission refuses an HDF5 file that holds them (registry/uploads.py). No other format is checked, so a class that loads a submitted pickle, joblib file or numpy array with allow_pickle must not reach tested.
    • Module roots. Admission gives a module to the entry with the longest matching root and refuses a module no root contains (Manifest.entry_for_module). A root that is not what the package ships makes its own classes unrunnable, a generic root such as app claims every module beneath it, and a root nested inside another entry's takes classes from it; nothing compares one entry's roots with another's (Manifest validates ids and requires). catalog.yaml's roots come from viva-catalog's package field, which registry/catalog.py copies without checking. Many of them do not match what the repository ships: a workspace whose package is pbg_<x> is recorded as viva_<x>, viva_Mgen is listed for a package that ships viva_mgen, and some omit a package the workspace also ships (a compatibility shim or a studies package). Take the roots from what the build backend ships (hatch or setuptools packages or packages.find, maturin module-name), not from the repository's name. A directory that exists in the tree is not proof that the wheel ships it: read the packaging settings.
    • Non-Python needs. What PyPI cannot supply (a Node.js bridge, MPI, a C++ engine) belongs under conda:. Two entries that list one conda package with different specs cannot share an environment: a mash-up of them is refused with a 409 at run time, and CI checks only the declared environments (registry/environments.py).
    • Step outputs. step-outputs-replace refuses a Step whose output ports add or append (float, integer, array, list, set and the like, also inside map[...]; environments/compliance.py). It runs when a built version is read back, so a Step that fails it is found only after the merge and costs a second pull request (viva-pde-particle#69, then a new pin). Reading its outputs() first avoids that.
    • Evidence and the case. evidence says what supports the level, and which commit it is about. The case's description should say where its expected values come from: a hand calculation (viva-basic-processes), a reference report (pbsim-common), or the package's own earlier output run through compose-api's runner (viva-pde-particle). load_cases returns an empty list for a directory it does not find, which looks the same as "no case", so the template's command prints each case with its problems.

    Levels¶

    The service runs a component whose level is tested or higher, as the manifest sets it or as a composed version computed it from the entry's cases (HPC_MINIMUM_LEVEL, registry/validation.py); listed and installable components do not run. Raising a level needs its evidence in evidence (the header of manifest.yaml). validated and curated need more, set out in docs/strategy.md, decision 5. Ask for the level the evidence supports and say which evidence it is; the reviewer decides.

    Accepted findings¶

    When a version's image is read back, generic checks run over its classes (environments/compliance.py), and a class that fails one is refused in that version. One check, step-outputs-replace, fails a Step whose outputs add or append, because a Step may fire more than once in a tick and would count its results twice. Some Steps add deliberately and cannot fire twice, for example one gated by update_condition to once per scheduled solve. An entry can accept such a failure for one of its own classes:

    accepted_findings:
  - component: v2ecoli.processes.metabolism.Metabolism
    check: step-outputs-replace
    reason: gated by update_condition to once per scheduled solve; its exchange deltas count once
    evidence: tests/test_metabolism_gate.py

    The finding stays on the version's record, marked with the reason, and the class is admitted. reason and evidence are both required; only an entry installed from git can accept a finding, only for its own classes (not a nested root's), and only step-outputs-replace (a class that does not import is never admitted). A composed version records the acceptances it was made with, and only those apply in it: a prebuilt or shared version accepts nothing. An acceptance therefore takes effect with a new version, which needs the entry's next commit (usually the one that adds the evidence test): a version of the same commit resolves to the same lock as the one before, and is not made (unless compose-api's runner has changed since, which makes a new version). evidence is a test in the entry's own repository, showing why the check's concern does not apply. A reviewer reads it as they would any evidence for a level. When a version is made, its lock Job checks first that each evidence path is a file at the entry's pinned commit (a private repository's through its token), and one that is not fails the version, saying which.

    A private repository¶

    An entry whose repository is private names the Auth0 role of the people who may use it, access_role: <role> (registry/access.py; docs/plan-private-repo-usage.md). Its metadata is in this public repository like any entry's, but the service hides it, its environments and their runs from everyone without the role, and refuses its classes to them as unregistered ones. CI refuses such an entry in the shared environment, a solver, a public entry's requires, a module root another entry shares, or with compliance-case files other than its document (tests/registry/test_access.py). The role itself is created and assigned in the BioSim Auth0 tenant.

    The service fetches the repository through its own GitHub App, compose-api-private-source, which reads repository contents and nothing else. The App is private to vivarium-collective, where an owner of the organization installs it on the repository. A repository in another organization needs the App made public, or an App of its own. The entry installs from git at a commit (install: {git, commit}). Each Job that locks or builds one of its versions gets a token for that version's private repositories alone, valid for an hour, in a Secret the Job owns. The build is made from a clone taken before it starts, so the token is in neither the image nor anything the service records. An environment's private repositories come from one organization. When no token can be had (the App is not installed, or GitHub is down), the request is a 503 and no version is recorded, so it can simply be made again (compose_api/environments/source_credentials.py).
