## 1. compose-api's environment model

### Two kinds of environment

`compose_api/registry/environments.yaml:20-29` declares two environments. Their `kind` is the literal
`shared | prebuilt` (`compose_api/registry/environments.py:37-40`).

| Name | Kind | What it is | Pinned by |
|---|---|---|---|
| `registry_env` | `shared` | One image, generated by pbest from a fixed list of libraries | the md5 of its generated definition |
| `viva-pde-particle` | `prebuilt` | An OCI image its owner publishes | digest, in `PREBUILT_SIMULATORS` (`kustomize/config/compose-api-rke/api.env:4`) |

- **The image is entered differently for each kind.**
  - `registry_env`: through the micromamba env.
  - `viva-pde-particle`: through the pixi shell hook, `/app/docker/shell-hook.sh`.

  The interface reader uses the matching command (`environments.yaml:23-29`).
- **Owner-published images.** A deployment can list them since 0.6.0 (#190). Only names in the setting are accepted,
  so a request can never pull an arbitrary image (`compose_api/simulation/prebuilt.py:20-21,35-42`).

### The submitter chooses the environment

The service does not derive the environment from the document. `POST /simulation/run` takes an optional
`simulator`:
- `None` means `registry_env`. pbest generates its definition from the pinned library list.
- A name means that prebuilt image: `compose_api/simulation/handlers.py:77-81`.

The run's `environment` label is `simulator or SERVICE_BUNDLE` (`compose_api/api/routers/simulation.py:102`).

### What is in the shared environment

- **Five libraries** (`compose_api/simulation/simulator_registry.json:1-34`):

  | Library | Version | From |
  |---|---|---|
  | python-copasi | 4.46.300 | PyPI |
  | tellurium | 2.2.11.1 | PyPI |
  | pb_multiscale_actin | 1.3.1 | PyPI |
  | readdy | 2.0.13 | conda-forge |
  | biosim-toolkit | 0.1.0 | PyPI |

- **Where the list comes from.** It is a copy of `biosimulations/registry` pinned at commit `f8b0132…`
  (`compose_api/simulation/simulator_registry.py:16-18`). biosim-toolkit was added locally *(survey: upstream `dev`
  still lists four)*.
- **How it is read.** `registry_dependencies()` splits the list into PyPI and conda dependencies (`:22-36`).
- **What else arrives.** pbsim-common, process-bigraph and bigraph-schema arrive through pbest's own requirements:
  `pbsim-common>=0.1.2`, `process-bigraph==1.0.5`, `bigraph-schema==1.0.14` (pbest 0.6.3 `METADATA`).

### Identity: the md5 of a recipe that does not reproduce

- **What the identity is.** The md5 of the generated Apptainer definition text (`compose_api/simulation/hpc_utils.py:87-88`).
  It is stored as `simulator.container_def_hash` (`compose_api/db/tables/simulator_tables.py:43-50`).
- **When it changes.** A hash not seen before inserts a new `simulator` row (`handlers.py:84-93`).
- **Prebuilt images.** The definition is just `Bootstrap: docker` / `From: <image>` (`prebuilt.py:28,45-49`).
  Pinned by digest, its hash is a function of the digest.
- **The shared image.** The hash names a recipe, not an artifact. The recipe is not deterministic (§2), so one hash
  can name different images built at different times.
- **Strategy decision 2** makes the OCI digest the identity. It is decided in principle and not implemented
  (`docs/strategy.md:148-170`; `docs/plan-container-runtimes.md:23-47`).

### Build flow and `environment_image`

`ensure_image` (`handlers.py:264-289`) checks for an available image. If there is none, it takes a Postgres lock on
the hash and calls `_download_or_build_container` (`handlers.py:300-368`). That function:
1. **Pulls if it can.**
   - A prebuilt image is pulled from its own reference.
   - The shared image is pulled from `simulator_image_repository:<hash>` (`:318-326`). Nothing is published there
     yet, so this pull fails and falls through (`docs/plan-container-runtimes.md:212-230`).
2. **Joins an in-flight build** of the same simulator, started by another API process or before a restart
   (`:339-347`).
3. **Otherwise starts a build** (`:348-359`).
   - Production uses a Kubernetes Job (`BUILD_BACKEND=k8s`, `api.env:12`).
   - The alternative is SLURM's `singularity build --fakeroot` (`compose_api/simulation/simulation_service.py:189`).

**Why Kubernetes.** The SLURM build node cannot build: there is no `/etc/subuid` entry for `svc_compose`
(`api.env:9-11`; `compose_api/simulation/build_k8s.py:4-6`).
- The Kubernetes build runs `apptainer build` as root in a **privileged init container** that mounts only scratch.
- An unprivileged container then copies the SIF onto the shared store as the service user
  (`build_k8s.py:83-91,130-150`).
- The build image is `ghcr.io/apptainer/apptainer:1.3.6` (`api.env:14`).

**Artifacts.** Each pulled or built image becomes an `environment_image` row (table at
`compose_api/db/tables/simulator_tables.py:71-84`; logic in `compose_api/simulation/images.py:72-106`):
- kind `sif` or `oci` (`compose_api/simulation/models.py:176-178`);
- location;
- `sha256` digest;
- size;
- the producing run;
- `available`.

Images are write-once: decision E4 (`docs/plan-environment-builds.md:52-53`).

**State of epoch 1.**
- Phases 1–4 are merged.
- Phase 4 adds `POST /registry/environments/{name}/build` and `GET /registry/environments/{name}/images`
  (`compose_api/api/routers/registry.py:179-208`). It merged in #297 on 2026-10-13. The status table in
  `plan-environment-builds.md:11` still says "in review".
- Phase 5, publishing to a registry, is deferred to EV12.

### The registry: manifest, catalogue, curation levels

- **`manifest.yaml` is the registry of record.** It has four curated entries: pbsim-common, pb-multiscale-actin,
  viva-pde-particle and biosim-toolkit, all at `tested` (`compose_api/registry/manifest.yaml:13-78`).
- **It overlays the generated `catalog.yaml`.** That file has 48 vivarium-collective wrappers at `listed`. The
  manifest wins on a shared id (`compose_api/registry/manifest.py:84-91`).
- **Each entry carries:**
  - a pin, by version or commit, which is required (`manifest.py:56-60`);
  - `module_roots`;
  - a `level`;
  - `bundles`, the environments it is installed in (`:44-54`).
- **The ladder** is `listed < installable < tested < validated < curated` (`manifest.py:23-37`;
  `docs/strategy.md:247-265`). HPC requires `tested` (`manifest.py:41`).
- **Levels are asserted, not computed.** Phase B's CI reads interfaces but does not yet compute levels
  (`docs/strategy.md:340`).
- **Interfaces are recorded per environment.** `registry-manifests.yml` runs process-bigraph-lang's
  `describe_env.py` inside each image and writes `manifests/<env>.json` in `pbg-interfaces/1`
  (`compose_api/registry/environments.yaml:1-18`; `.github/workflows/registry-manifests.yml:52,82`).

### Compatibility: the address allow-list is the only check

There is no dependency graph, resolver or conflict detection anywhere in the service. The one check is at submission.

`check_address` (`compose_api/registry/validation.py:132-141`) runs two tests.

**`_unsafe_reason` (`:104-112`).** These are always refused:
- a protocol other than `local`;
- non-string address data;
- the arbitrary-import form `local:!`.

**`_registry_reason` (`:115-129`).** It requires all of the following:
- a qualified `module.Class`;
- an entry owning the longest matching module root;
- that entry at `tested` or higher;
- that entry's `bundles` containing `SERVICE_BUNDLE = "registry_env"` (`manifest.py:20`).

**Prebuilt submissions skip both tests today**, the unsafe forms included (`compose_api/api/routers/simulation.py:105-121`).
This gap is noted at `docs/strategy.md:331-333` and `docs/plan-container-runtimes.md:205-210`.
- PR #315 (`fix/prebuilt-and-comparisons-checks`, **open** as of 2026-10-13) changes this. Prebuilt submissions
  would skip only the registry lookup (`validate_submission(..., registry=False)`) and get a 400 for `local:!` and
  non-`local` addresses.
- The citations above describe `main` before that merge.

### What the strategy plans

- **Membership rule.** `registry_env` grows only while additions co-install. The first conflict is the signal to
  build the per-composite resolver (`docs/strategy.md:298-310`).
- **Order of preference** (`docs/strategy.md:283-296`):
  1. one environment per composite;
  2. cached bundles;
  3. splitting across containers.
- **Phases** (`docs/strategy.md:337-346`):
  - C, the resolver, is gated on digest identity.
  - D, two containers, is grant row `A3.4.docker`.
  - Neither has started.
- **Vestigial tables.** `package`, `bigraph_compute` and `allow_list` still exist
  (`compose_api/db/tables/package_tables.py:48,76,133`), as does `simulator_to_package`
  (`compose_api/db/tables/simulator_tables.py:102`). The lookup that used them is commented out (`handlers.py:87-91`).

## 2. pbest: how the container definition is generated

All citations below are to `pbest/containerization/` in pbest 0.6.3.

- **Entry point.** `generate_container_def_file(deps, engine)` (`container_constructor.py:106-117`) renders a
  Dockerfile from a Jinja template (`:46-78`). It then converts the Dockerfile to Apptainer syntax with spython's
  `DockerParser` / `SingularityWriter` (`:89-103`).
- **It concatenates; it does not resolve.**
  - All PyPI dependencies go into one `micromamba run … python3 -m pip install 'a==v' 'b==v'` line (`:51-63`).
  - Each conda dependency gets its own `micromamba install -c conda-forge … <pkg>=<v> python=3.12 --yes` line
    (`:64-68`). Every conda line re-pins `python=3.12`, and nothing checks them against each other or against the
    pip line.
  - pbest's own requirements are installed **after** the user dependencies (`generic_container.jinja:22-25`). A
    later `pip install` can silently replace a version the user pinned.
- **Resolution happens at build time.** The template clones pbest at a tag and runs
  `uv pip compile pyproject.toml -o requirements.txt` inside the build (`generic_container.jinja:9-10`). The
  transitive versions are whatever PyPI offers on the day of the build.
- **The template is not reproducible** (`generic_container.jinja:1-28`):
  - `FROM astral/uv:python3.12-bookworm-slim`, a mutable tag (`:1`);
  - `apt update` / `apt upgrade -y`, unpinned (`:3-4`);
  - micromamba from a `linux-64/latest` URL (`:15`), which also fixes the image to amd64;
  - the build-time `uv pip compile` above.

  `pbest_tag` defaults to `0.6.3` (`container_constructor.py:48`).
- **The dependency model** is two lists of `ExperimentDependency(name, url, type, version)`
  (`pbest/utils/input_types.py:36-59`). An empty version means any version (`:46-47`). `ContainerizationTypes.MULTIPLE`
  is declared (`:9-12`) and used nowhere *(survey)*.
- **A dormant prototype.** `dependency_resolution/discovery.py` parses addresses that carry their own dependencies,
  such as `python:pypi<pkg[ver]>@module.Class`. It always returns empty dependencies *(survey; not re-read)*.
- **A live upstream fetch.** pbest's own `_default_registry_deps()` fetches `registry.json` from the `dev` branch of
  `biosimulations/registry` on every call (`container_constructor.py:21-43`). compose-api avoids this by passing
  its pinned copy.

## 3. process-bigraph: running processes out of process

Read from `vivarium-collective/process-bigraph` `main` at `8ce2e1d`. bigraph-schema line numbers are from the survey
and were not re-read.

### Addresses and protocols

- **Parsing.** An address is `protocol:data`, and a bare string means `local` *(survey: bigraph-schema
  `schema.py:15-38`)*.
- **Lookup.** `local:a.b.C` is looked up in `core.link_registry`, and `local:!` imports the module directly
  *(survey: `protocols.py:23-43`)*.
- **Extension.** Protocols are pluggable: a registered type plus a `load_protocol` dispatch.

`process_bigraph/protocols/__init__.py:13-17` registers four protocols.

| Protocol | Mechanism | Separate environment? | Wire format |
|---|---|---|---|
| `parallel` | `multiprocessing` Pipe, one child per process; `forkserver` on Linux, `spawn` on macOS/Windows (`parallel.py:113-124`) | **No.** Same interpreter and packages | pickled `(command, args, kwargs)` tuples (`parallel.py:56-61,140`) |
| `rest` | `requests` GET/POST to `/process/<name>/{config-schema,initialize,inputs,outputs,update,end}` (`rest.py:23-31,55-67,165`) | Yes, if the server runs elsewhere | raw JSON; no status check before `.json()` |
| `ray` | actor pools for `local:RayProcess`; sharded batch actors (`batch_update` per shard) for `ray:` | **No.** No `runtime_env` anywhere in `ray.py` (grep, 2026-10-13), so actors share the driver's stack | Ray's pickling |
| `git:owner/repo@ref#module:callable` | fetch and pin the repo to a SHA, build a `uv venv` per SHA, run a worker subprocess (`git.py:1-34`) | **Yes.** The only cross-environment protocol in core | newline-delimited JSON over stdio (`git.py:517,528`; `_git_worker.py:93`) |

- **`git:` trust.** Repositories off an allow-list are refused. The allow-list defaults to `CovertLab/vEcoli`
  (`git.py:26-29`), and a conformance check runs before any run (`:31-33`).
- **`git:` isolation.** It is subprocess + venv, not a container. Its design spec deferred container isolation
  *(survey: choice D1(b) in `docs/superpowers/specs/2026-07-31-git-remote-protocol-design.md`)*.
- **`git:` events.** `PBG_*` trace variables reach the child, but the worker emits no events *(survey)*.

### The `parallel.py` result bug: not a bug

The survey reported that `get_command_result()` only calls `recv()` when `_pending_command` is set, and that
`send_command` never sets it. **Verdict: not a bug.**
- `ParallelProcess.send_command` calls `self.pre_send_command(command, args, kwargs)` when `run_pre_check` is true,
  which is the default (`parallel.py:126-136`).
- `pre_send_command` is inherited from `Open` and sets `self._pending_command = command, args, kwargs`
  (`composite.py:389-412`).
- So `get_command_result` (`parallel.py:144-171`) sees a pending command and calls `self.parent.recv()` (`:167`).
- `invoke()` sends `update` without waiting (`:226-228`). The scheduler's later `.get()` (`:173-174`) receives the
  reply.

The survey missed the inherited pre-check. Nothing was filed upstream.

### Nesting

- **A Composite is a Process.** Its `bridge` maps outer ports to inner wires *(survey: `composite.py`, the `Composite`
  class at `:1236`, bridge handling `:1360-1431`)*.
- **Consequence.** A sub-composite can be the unit placed in another environment, because the composite boundary is
  already a port boundary.

### No transport uses schema serialisation

- **bigraph-schema has schema-aware `serialize`, `realize` and `bundle`** *(survey: `core.py:783-790`)*.
- **No transport calls them.** `parallel` and `ray` pickle, and `rest` and `git:` send raw JSON.
- **Consequences:**
  - numpy arrays, units and typed structures do not cross a JSON boundary intact.
  - Pickles do not cross a NumPy 1/2 boundary. NumPy 2 pickles reference `numpy._core`
    ([numpy commit](https://github.com/numpy/numpy/commit/bdb190d8cf3ad2d8d6fd9264852ba35d71cf7417)).

### Outside core

- **`vivarium-collective/docker-process`:** JSON over TCP to a Docker container. Last pushed 2025-12 *(survey)*.
- **`rest-process` and `julia-process`** *(survey)*.
- **Per-wrapper bridges.** Wrappers such as chaste, tstmd, medyan and artistoo carry their own Docker or subprocess
  bridges *(survey)*.

None of these runs under Apptainer on SLURM.

## 4. The workbench and viva-api

vivarium-workbench `main` at `46b35af`.

- **Workspaces.** A workspace is a git checkout with a `workspace.yaml` (`vivarium_workbench/lib/workspace_yaml.py`).
- **One uv venv per workspace.**
  - `env_resolver.py` uses `<ws>/.venv` (`.venv/bin/python` or `.venv/Scripts/python.exe`). For a git worktree it
    uses the main checkout's `.venv`. Otherwise it falls back to the running interpreter (`lib/env_resolver.py:7,35,64-85`).
  - There is no pixi or conda path.
- **Installing a module.** It installs a module's `uv.lock` through `uv export --frozen | uv pip install`, so
  installs only add packages *(survey: `lib/catalog_install_views.py:105-135`)*.
- **Isolation.** All workspace code runs in a pooled env worker keyed by `(workspace, interpreter)`
  (`lib/env_worker_pool.py`).
  - Locally, the worker is a subprocess in the workspace venv.
  - Hosted, it is a Kubernetes Job running the simulator's prebuilt image for `(repo, commit)`, with the worker
    module injected by an init container *(survey: `docs/env-worker-runtime.md:24-70`; viva-api
    `viva_core/env_worker/service.py:104-158`, unverified)*.
- **The principle.** "The image *is* the environment coordinate"; rebuilding it locally "is a second source of truth
  that can drift" (`docs/REFACTOR-PLAN.md:826-833`).
- **Fingerprinting.** `lib/env_fingerprint.py` records the git HEAD, the `uv.lock` hash, the core package versions
  and an `env_id()` digest *(survey)*.
- **Comparisons.** "A run pins exactly one environment coordinate — but an investigation's member runs may pin
  *different* coordinates" (`docs/dual-engine-comparison.md:68-70`).
- **No compatibility solver.**

Both the workbench and compose-api's prebuilt path already treat a commit-pinned image as the environment, with one
worker per environment. Neither runs one composite across two environments.

## Constraints on the design

1. **Identity is a recipe hash, and the recipe does not reproduce.**
   - The causes are a mutable base tag, `apt upgrade`, micromamba `latest` and a build-time `uv pip compile`.
   - Digest identity (decision 2) is decided but not built.
   - The resolver (phase C) is gated on it.
2. **The two deployed islands already run incompatible cores** (1.0.5/1.0.14 vs 1.8.5/1.7.0).
   - pbest's exact pin holds `registry_env` back.
   - Every middleware package needs ≥ 1.4.12.
3. **pbest concatenates; it does not resolve.**
   - Each conda line re-pins Python.
   - pbest's own requirements install last and can override user pins.
4. **Validation hard-codes one bundle and one protocol.**
   - Any multi-environment, `git:` or `rest:` composite is refused today.
   - Prebuilt submissions skip validation entirely until PR #315 merges.
5. **The submitter, not the document, selects the environment.**
6. **The catalogue carries no environment metadata.** 38 of 50 wrappers float on git `main`, so pinning has to happen
   in compose-api, as `catalog.yaml` already does.
7. **pip alone cannot build the forest.** Several engines come from conda only, Rust, Node, Java, Docker sidecars or a
   compiler at run time.
8. **The cluster cannot build images with fakeroot.**
   - Builds run in a privileged Kubernetes Job.
   - Nothing is published to a registry yet.
   - Both images in use are linux/amd64 only.
9. **Out-of-process transports exist, but none fits HPC isolation.**
   - `git:` (uv venv + stdio), `rest:` and `docker-process` all exist.
   - None serialises through the schema.
   - None is a container protocol in core.
   - `parallel` and `ray` give no environment isolation.
10. **The workbench and viva-api treat a commit-pinned image as the environment,** with one worker per environment.
    compose-api's prebuilt path does the same.

## Unknowns

- **No compatibility data exists.** There is no matrix and no resolver output. No record shows which items
  co-install. Curation levels are asserted.
- **How to identify an item apart from a package.** Entries are keyed by module root. The catalogue counts classes but
  not their dependencies.
- **Whether `registry_env` survives process-bigraph ≥ 1.8.** Its SED-ML and manifest suites have not been run
  against a modern core (experiment X5).
- **No wire protocol for a composite split across containers on SLURM.** Networking between Apptainer instances
  inside one job, or across jobs, is untested.
- **Whether a `git:`-style stdio worker generalises to an image or a SIF**, and which side owns typed serialisation.
- **Whether Mantis offers Enroot/Pyxis or Apptainer's OCI mode.** The `plan-container-runtimes.md` §6 questions are
  still unasked.
- **Unverified here:** viva-api internals (private), bigraph-schema line numbers, and the catalogue survey's counts.
  Which Python and numpy combinations actually co-install across wrappers was read from manifests, not tested.
