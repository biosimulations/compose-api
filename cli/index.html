    The compose-api command line¶

    compose-api drives the compose-api service from a terminal or a script: sign up or in through Auth0 in your browser, keep the session in your operating system's credential store, submit simulations, wait for them, fetch their results, and inspect what the service has registered. It covers every operation in the API (a test fails if an operation is added without a command). How it is built and why: plan-cli.md.

    Signing in identifies you to the API. It does not make your simulations private: anyone with a simulation's numeric ID can read its status and results (see Authentication). Roles are labels on your identity, not access controls on simulations.

    Install¶

    $ pip install 'compose-api-client[cli]'      # or: uv tool install 'compose-api-client[cli]'
$ compose-api --help

    The base package (pip install compose-api-client) is the Python client alone: httpx, attrs and python-dateutil, no server dependencies. The [auth] extra adds the Auth0 / keyring session layer, and [cli] includes [auth] plus the terminal UI. In this repository, uv run compose-api ... works with no install.

    Connect and Profiles¶

    Setting Option Environment Default
    Profile --profile COMPOSE_API_CLI_PROFILE production
    Service --url COMPOSE_API_URL the selected profile's api_base_url
    HTTP timeout --timeout COMPOSE_API_TIMEOUT 300 s (downloads; other requests cap at 60 s)
    Output -o/--output auto\|table\|json COMPOSE_API_OUTPUT auto: a table on a terminal, JSON when piped
    Automation token — (env-only) COMPOSE_API_TOKEN none (uses stored session, else anonymous)

    Global options go before the command: compose-api -o json status 4192. Results go to stdout; progress lines and errors go to stderr, so compose-api -o json ... | jq always sees clean JSON.

    A profile says which API to call and how to sign in to it. Two are built in:

    Profile API Auth0 audience Client ID
    production (default) https://compose.cam.uchc.edu https://api.compose.cam.uchc.edu 1FV43fysEjhTrYYRNaMEGvCteu4g2ay4
    local https://api.compose-api-local https://api.compose.local Fp3QmULWNIhdutlBRVFm2HjPGapqdnKV

    Both use the tenant dev-bu7yo7484tyxu6a1.us.auth0.com, the database connection Username-Password-Authentication, the Google connection google-oauth2 and callback port 8400. The client IDs belong to public native applications: they are identifiers, not secrets, and there is no client secret anywhere in the CLI.

    Choose a profile with --profile NAME or COMPOSE_API_CLI_PROFILE. Each setting is then taken from its environment variable, else from [profiles.<name>] in config.toml (under your user configuration directory), else from the built-in value. compose-api config show prints every effective value and where it came from.

    Setting Environment variable Meaning
    api_base_url COMPOSE_API_CLI_API_BASE_URL The API origin. https only, except a loopback host (http://localhost:8000). No path, query or credentials.
    auth0_domain COMPOSE_API_CLI_AUTH0_DOMAIN The tenant's bare host. The issuer is derived from it.
    auth0_audience COMPOSE_API_CLI_AUTH0_AUDIENCE The API identifier, exactly as the server's AUTH0_AUDIENCE. It is not the URL you call.
    auth0_client_id COMPOSE_API_CLI_AUTH0_CLIENT_ID The native application's public client ID.
    database_connection COMPOSE_API_CLI_DATABASE_CONNECTION Optional: steers --provider email to this connection.
    google_connection COMPOSE_API_CLI_GOOGLE_CONNECTION Needed for --provider google in the browser.
    callback_port COMPOSE_API_CLI_CALLBACK_PORT The registered loopback callback port, http://127.0.0.1:<port>/callback. Default 8400.
    ca_bundle COMPOSE_API_CLI_CA_BUNDLE Absolute path to extra CA certificates (PEM) for an API with a private CA.

    Sign up and sign in¶

    Passwords, MFA, email verification and Google consent all happen on Auth0's pages in your own browser. The CLI never asks for a password, and never accepts a password or --token flag on the command line.

    compose-api auth signup                     # create an email-and-password account
compose-api auth signup --provider google   # first sign-in with Google creates the account
compose-api auth login                      # returning user: choose email or Google on the page
compose-api auth login --provider google
compose-api auth login --method device      # sign in on another device (SSH, containers)
compose-api auth status                     # what is stored locally; contacts nothing
compose-api auth status --verify            # renews if needed and asks GET /auth/me to confirm the identity
compose-api auth logout                     # revokes the refresh token with Auth0, then erases the session
compose-api auth logout --local-only

    --method chooses how a sign-in reaches you: auto (the default) picks from the environment: the device code over SSH (SSH_CONNECTION), on a headless host or in a GitHub Codespace, and the browser otherwise. Over SSH or without a display, a recognized VS Code bin/helpers/browser.sh or browser.cmd helper, or WSL's wslview, still gets the browser, since they forward the callback port. VS Code or WSL environment markers alone do not qualify: a text browser, an unknown command or a fallback list in $BROWSER gets the device code. An unrecognized helper can still be chosen explicitly with --method browser. A Codespace still gets the device code, because one opened in a web browser cannot receive the callback. Whenever auto picks anything but your desktop's browser, the command says why and how to choose another way. browser opens the system browser, or $BROWSER without a display. A text browser there (w3m, lynx, links, elinks, www-browser) would take over the terminal, so it counts as none and the command says to use url or device. url prints the sign-in link instead of opening anything; device is RFC 8628, for signing in on another device. The same option works with --ephemeral-auth before any command.

    The session is one record in your operating system's credential store (macOS Keychain, Linux Secret Service or Windows Credential Manager), under compose-api.cli.v1.<digest>. Plaintext and unknown keyring backends are refused; there is no file fallback. On hosts without a credential store, use --ephemeral-auth before the command (for example compose-api --ephemeral-auth --method device simulators list), which signs in for a single command in memory without requesting a refresh token.

    The browser flow listens on http://127.0.0.1:8400/callback, the only callback the tenant's applications register, so COMPOSE_API_CLI_CALLBACK_PORT cannot move it. If port 8400 is already in use, sign-in stops before the browser opens; over SSH, ssh -L 8400:127.0.0.1:8400 forwards the callback to your own computer, which makes --method url work there.

    For CI and non-interactive automation, set COMPOSE_API_TOKEN in the environment. When set, it takes precedence over a stored session for the active profile (printing a one-line notice to stderr), is never renewed or printed, and is still bound by the destination guard (_DestinationGuard), redirect refusal (follow_redirects=False) and environment isolation (trust_env=False). If --url is overridden to an origin different from the profile's api_base_url, neither a stored session nor COMPOSE_API_TOKEN is sent to it.

    A run, start to finish¶

    $ compose-api run experiment.omex --simulator viva-pde-particle --wait --download out/ --extract
submitted simulation 4195
    0s simulation 4195: submitting
    5s simulation 4195: running (slurm 4137519)
   31s simulation 4195: completed (slurm 4137519)
{ "simulation_id": 4195, "status": "completed", ..., "files": ["out/results_2026-10-07#08-24-19.pber"] }

    Or in steps:

    $ compose-api run experiment.omex --simulator viva-pde-particle     # prints simulation_database_id
$ compose-api status 4195                                            # "submitting" until the SLURM job exists
$ compose-api wait 4195
$ compose-api results 4195 --extract out/

    Once signed in (compose-api auth login), every command sends the profile's session; without one, commands call the API anonymously, as it allows. Neither ever starts a sign-in on its own:

    compose-api simulations list                               # with the stored session, or anonymously
compose-api --ephemeral-auth run experiment.omex           # sign in for this one command; keep nothing
    • Simulation ids. A simulation id is what run prints (simulation_database_id), and what status, wait, results, events, trace and datasets list --sim take. To find one later:

    console $ compose-api simulations list # newest first, with status and SLURM job $ compose-api simulations list --status running --since 6h $ compose-api simulations list --simulator viva-pde-particle --limit 20 $ compose-api simulations list --label source:biomodels --tag repressilator $ compose-api simulations show 4334 # plus how many events and datasets it recorded

    Runs carry labels, written by the service (source, environment, solver, model, ...), and tags and a description given at submission: compose-api run x.omex --tag demo --tag repressilator --description "...". --label key:value and --tag filter the list; each is repeatable, and all must match. - --simulator names a prebuilt simulator image the service is configured with. Without it, the service builds one from the document's dependencies, and build-status <simulator_database_id> follows that build. - status takes several ids and asks for them in one call. - curated copasi and curated tellurium run an SBML model with those simulators. - simulators list, processes list and steps list show what is registered. - openapi --diff reports whether this client and the live service disagree on the API.

    JSON output¶

    Every command takes --json, which prints JSON instead of a table. It's the same as --output json before the command name, and it overrides that option. The auth commands accept --json without listing it in their help: -o json is the spelling documented for them. JSON is also the default whenever output isn't a terminal, so compose-api simulations list | jq needs neither.

    What a run did: events and traces¶

    Every run records events: the service's own (dispatch.submitted, then slurm.<state> on each change), the job script's (job.start, and job.end with the exit code, inside a job span), and, if the simulator is built on process-bigraph 1.8.5 or later, the engine's (run.start, run.end, process.exception, its spans).

    $ compose-api events 4195                  # everything recorded so far
$ compose-api events 4195 --follow         # and new ones as they arrive, until the job has finished
$ compose-api events 4195 --level error    # only what went wrong
$ compose-api trace 4195                   # the spans as a tree, each with its own events
$ compose-api trace 4195 --chrome t.json   # a file for ui.perfetto.dev

    With --output json, events prints JSON lines, one event per line. The service reads a run's events while it runs and for a few minutes after it ends, so a --follow may print a last few events after the job is done.

    What a run produced: datasets¶

    Each file a run leaves in its output/ directory, and its results.zip, is a dataset. The job script records each with its size and sha256 when the run ends. A simulator can announce its own files with an artifact.written event, adding a kind, a name and attributes.

    $ compose-api datasets list --sim 4195            # one run's files
$ compose-api datasets list --kind results         # every results file you can read
$ compose-api datasets show <id>
$ compose-api datasets get <id> -O out/            # just that file, not the whole archive

    A run's SLURM log is a dataset too (job.out, kind log): compose-api datasets list --sim 4195 --kind log, then datasets get on its id. A dataset is readable by whoever can read its simulation.

    Output and exit status¶

    Results go to stdout; progress, prompts and human error lines go to stderr. With --json, an error is also printed to stdout as {"error": {"category": ..., "message": ..., "exit_code": ...}}.

    Exit Category Meaning
    0 Success; with --wait, the job completed
    1 not_found, invalid_request, server_error, api_error, job_failed, uncertain, internal The API answered unsuccessfully (404, 400/422, 500, other), the job ended other than completed, a submission outcome was ambiguous, or the CLI hit an internal bug
    2 usage A malformed command line, a removed option (--token), or a file argument that cannot be used
    3 authentication No session, an expired one that cannot be renewed, a refused or cancelled sign-in, or credentials the API rejected
    4 forbidden The API refused the request for this account (403)
    5 network, rate_limited, uncertain Auth0 or the API could not be reached, timed out, is unavailable (502/503/504), or is rate limiting (429)
    6 configuration, storage, protocol, interaction A profile, credential-store, protocol or local-browser problem
    7 wait_timeout --wait-timeout passed before the job finished
    130 Cancelled (Ctrl-C)

    So compose-api run x.omex --wait && next-step runs next-step only if the simulation completed.

    From Python¶

    The command line is a thin layer over compose_api_client.ext, which applications can use directly:

    from compose_api_client.ext import ComposeSession

with ComposeSession() as s:  # https://compose.cam.uchc.edu
    sim, state, files = s.run_and_wait("experiment.omex", simulator="viva-pde-particle", dest="out/", extract=True)

    AsyncComposeSession has the same methods as coroutines, and AsyncComposeSession.in_process(app) runs against a FastAPI app in a test with no network.

    compose-api run¶

    Submit a simulation. Prints its ids; with --wait, its final state (and the files, with --download).

    Usage:

    $ compose-api run [OPTIONS] DOCUMENT

    Arguments:

    • DOCUMENT: The .omex (or .pbg) to run. [required]

    Options:

    • --simulator TEXT: A prebuilt simulator image by name (the older form of --environment).
    • --environment TEXT: The environment to run in (environments list); omitted: inferred from the document's classes.
    • --interval FLOAT: Simulation interval passed to the runner. [default: 1.0]
    • --batch / --no-batch: Submit as a batch job (smaller partition, 1 CPU). [default: no-batch]
    • -t, --tag TEXT: A tag to find the run by later (repeatable).
    • --description TEXT: What the run is for.
    • --environment-version INTEGER RANGE: The version of the environment to run in (registry_env@3 is 3); omitted: its default. [x>=1]
    • --visibility [private|public]: private (the default signed in: you and admins) or public (anyone); anonymous runs are public.
    • -w, --wait: Wait for the job to finish; exit 1 unless it completed.
    • -d, --download PATH: With --wait: save the results archive into this directory.
    • --extract / --no-extract: With --download: unpack the archive instead of saving the zip. [default: no-extract]
    • --poll FLOAT: Seconds between status checks. [default: 5.0]
    • --wait-timeout FLOAT: Give up waiting after this many seconds (exit 5).
    • --json: Print JSON (the same as --output json).
    • --help: Show this message and exit.

    • NAME: The suite, e.g. biomodels-ode-sample. [required]
    • SOURCE: The suite's source, e.g. biomodels:BIOMD0000000039. [required]

    Options:

    • --category TEXT: What kind of problem, e.g. NONINTEGER_STOICH. [required]
    • --reason TEXT: Why it fails or differs. [required]
    • --solver TEXT: The solver it applies to; omit for a problem of the whole source.
    • --seen-run INTEGER: The suite run it was first seen in.
    • --json: Print JSON (the same as --output json).
    • --help: Show this message and exit.

    • --provider [email|google]: Identity provider: email or google. With --method device it is advice: the page chooses. [default: email]
